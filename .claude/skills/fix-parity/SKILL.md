# Fix Parity — Automated Parity Issue Resolver

Consume the parity report(s) generated by `/parity-report`, plan fixes, and launch parallel agents in isolated git worktrees to resolve every flagged issue. The goal is **zero open parity issues** — every LOGIC_DIFF, PARAM_DIFF, PARTIAL, and MISSING item must be addressed.

---

## Step 0: Read and Analyze Parity Reports

### 0a. Locate Reports

Use Glob to find all files matching `parity-reports/parity-report-*.md` in the repo root. Sort by date (newest first).

- If `$ARGUMENTS` is a filename (e.g., `parity-report-2026-02-26.md`), use only that report.
- If `$ARGUMENTS` is a module name (e.g., `drik`, `yoga`), use the latest report but filter to only that module's tasks.
- If no argument, use the latest report. If multiple reports exist, also load the second-latest for cross-referencing.

### 0b. Cross-Reference Multiple Reports (if available)

When two or more reports exist, compare them to identify **persistent issues** — problems that appear in BOTH reports. These get elevated priority because they were not fixed between report runs.

For each task in the latest report:
1. Search the previous report for the same function (match by `pyFile` + `function` name).
2. If found with the same status (e.g., LOGIC_DIFF in both) → mark as **PERSISTENT** and elevate priority by one level (LOW→MEDIUM, MEDIUM→HIGH, HIGH stays HIGH).
3. If found in the previous report but NOT in the latest → it was fixed, skip it.
4. If only in the latest report → it's **NEW**, keep its original priority.

Create a **consolidated task list** with this structure:

```
{
  "reportSource": "parity-reports/parity-report-2026-02-26.md",
  "comparedWith": "parity-reports/parity-report-2026-02-20.md" | null,
  "tasks": [
    {
      "id": "drik-001",
      "function": "_get_tithi",
      "type": "LOGIC_DIFF",
      "priority": "HIGH",
      "persistent": true,
      "pyFile": "src/jhora/panchanga/drik.py",
      "pyLine": 200,
      "tsFile": "pyjhora-web/src/core/panchanga/drik.ts",
      "tsLine": 100,
      "description": "Python uses (a * b + c) // d, TS uses (a * b + c) / d",
      "module": "drik",
      "category": "panchanga",
      "dependencies": []
    }
  ]
}
```

### 0c. Parse the Report

Extract tasks from the report by parsing:

1. **Implementation Tasks sections** — look for ` ```task ` code blocks within each module report (between `---BEGIN_MODULE_REPORT---` and `---END_MODULE_REPORT---` markers).
2. **Consolidated Implementation Plan** — the aggregated task list at the end of the report under "Critical (HIGH Priority)", "Important (MEDIUM Priority)", and "Backlog (LOW Priority)".
3. **LOGIC_DIFF detailed explanations** — extract the exact Python vs TS code snippets and the suggested fix for each difference.
4. **MISSING in TS tables** — extract function names, descriptions, and priority.
5. **PARAM_DIFF tables** — extract function names and what parameters differ.
6. **PARTIAL tables** — extract function names and what's missing.

If a task appears in both the per-module section and the consolidated plan, prefer the per-module version (it has more detail).

## Step 1: Plan Work Packages

Group tasks into **work packages** — sets of tasks that can be fixed together by a single agent because they touch the same TS file. Each work package becomes one agent assignment.

### Grouping Rules

1. **Group by TS file**: All tasks for the same `tsFile` go into one work package.
2. **Respect dependencies**: If task A depends on task B, they must be in the same work package OR task B's package must run first.
3. **Size limits**: No single work package should have more than 15 tasks. If a file has more, split by function proximity (group functions that call each other).
4. **Large file handling**: For large TS files (drik.ts, yoga.ts, charts.ts, house.ts), create ONE dedicated work package per file — do not split across agents (to avoid merge conflicts).

### Priority Ordering

Within each work package, order tasks:
1. **PERSISTENT + HIGH** first (recurring critical issues)
2. **HIGH** (new critical issues)
3. **PERSISTENT + MEDIUM** (recurring important issues)
4. **MEDIUM** (new important issues)
5. **PERSISTENT + LOW** (recurring minor issues)
6. **LOW** (new minor issues)

Within the same priority, order by dependency (independent tasks first, then dependent ones).

### Cross-File Dependencies

If a work package depends on another (e.g., fixing a helper in `constants.ts` that `drik.ts` uses):
1. Mark the dependency between work packages.
2. The dependent package's agent must wait for the dependency to complete.
3. Use the Task tool's `addBlockedBy` to enforce this.

---

## Step 2: Create Task Tracking

Use `TaskCreate` to create a task for each work package. Include:
- **subject**: `Fix parity: {module} ({N} issues)`
- **description**: Full list of tasks in the package with their IDs, functions, types, and descriptions
- **activeForm**: `Fixing {module} parity issues`

Set up `addBlockedBy` relationships for any cross-file dependencies.

Also create a master task:
- **subject**: `Parity fix orchestration — {total} issues across {N} modules`
- **description**: Summary of all work packages, blocked by all individual work packages

---

## Step 3: Launch Parallel Fix Agents

For each work package, launch a Task agent with:
- `subagent_type: "general-purpose"` (needs read + write + bash access)
- `isolation: "worktree"` (each agent gets its own git worktree)
- `team_name` if using teams

**IMPORTANT**: Launch work packages in parallel ONLY if they have no dependencies between them. If package B depends on package A, launch B only after A completes.

Launch independent packages in batches of 3-5 agents maximum to avoid system overload.

### Agent Prompt Template

Each fix agent receives:

```
You are fixing Python↔TypeScript parity issues in the PyJHora project.
You are working in an isolated git worktree. Your changes will be on a dedicated branch.

## Setup

1. `cd pyjhora-web && npm install` — install dependencies in the worktree
2. Run `npx vitest run` to verify tests pass BEFORE making any changes. If tests fail before your changes, note which ones and do not count those as regressions.

## Your Work Package

**Module**: {module}
**Category**: {category}
**TS File**: {tsFile}
**Python Reference**: {pyFile}

### Tasks to Fix (in order):

{For each task in the work package:}

#### Task {id}: {type} — `{function}`
**Priority**: {priority} {persistent ? "(PERSISTENT — unfixed across multiple reports)" : ""}
**Python** (`{pyFile}` L{pyLine}):
{description with exact code/formula from the parity report}
**TypeScript** (`{tsFile}` L{tsLine}):
{current TS code if available}

{detailed fix description from the parity report}
**Dependencies**: {list or "none"}

---

## Instructions

### How to Fix Each Task

1. **Read the Python source** at the specified line number. Understand the COMPLETE logic of the function — not just the flagged line, but the entire function.
2. **Read the TS source** at the specified line number. Understand what it currently does.
3. **Implement the fix** in the TS file:
   - For LOGIC_DIFF: Change the TS logic to exactly match the Python logic. Translate Python idioms to TS equivalents (`//` → `Math.floor()`, `range()` → `for` loop, etc.) but the SEMANTICS must be identical.
   - For PARAM_DIFF: Add missing parameters with the same defaults as Python. Update the function body to use them.
   - For PARTIAL: Complete the missing branches, conditions, or logic paths that exist in Python but not in TS.
   - For MISSING: Port the entire function from Python to TS. Follow existing TS conventions in the file (naming, style, exports).
4. **Check dependencies**: If the function calls other functions, verify those are correctly ported too. If they're in your task list, fix them first. If they're in another work package, note the dependency.
5. **Preserve existing TS patterns**: Match the code style, naming conventions, and structure already used in the TS file. Use camelCase for function names, PascalCase for types.

### Testing Protocol

After EVERY group of related fixes (or after every single fix for HIGH priority items):

1. Run `cd pyjhora-web && npx vitest run` to verify all tests pass.
2. If tests fail:
   - If the failure is in a test that was already failing before your changes (from the baseline run), ignore it.
   - If the failure is caused by your change, FIX IT before moving on. Do not proceed to the next task with broken tests.
   - If you cannot fix the test failure, REVERT your change and document why in the skip report.
3. If tests pass, commit your changes.

### Commit Protocol

Create **logical commits** — one commit per logical unit of work:

- If fixing a single function: one commit for that fix
- If fixing a group of tightly related functions (e.g., a helper + the function that calls it): one commit for the group
- Commit message format: `fix(parity): {brief description of what was fixed}`
  - Example: `fix(parity): align _get_tithi formula with Python floor division`
  - Example: `fix(parity): port missing _helper_func to drik.ts`
  - Example: `fix(parity): add missing param 'c' to specialAscendant with default true`

**CRITICAL**: Every commit must leave the project in a working state (tests pass). NEVER commit code that breaks tests.

After committing, run tests again to confirm the commit is clean.

### Skip Protocol

If you CANNOT fix a task, you MUST document it. Do NOT silently skip anything.

Create or append to a file called `parity-reports/fix-parity-skipped-{date}.md` in the repo root:

```markdown
## Skipped: {task-id} — `{function}`
**Reason**: {detailed explanation of why this cannot be fixed}
**Options**:
- {what would need to change to make this fixable}
- {alternative approaches considered}
**Impact**: {what downstream functions are affected}
```

Valid reasons to skip:
- The fix requires a sync ascendant function which doesn't exist in TS (known limitation)
- The fix requires an external library not available in the browser (e.g., Python `ephem`)
- The Python code has a known bug that TS intentionally does NOT replicate
- The fix would require architectural changes beyond this task's scope (document what's needed)

Invalid reasons to skip:
- "Too complex" — break it into smaller steps
- "Not sure how it works" — read the Python code more carefully
- "Tests are failing" — fix the tests or revert your change

### Completion

When all tasks are done (or skipped with documentation):

1. Run the full test suite one final time: `cd pyjhora-web && npx vitest run`
2. Report back with:
   - Number of tasks fixed
   - Number of tasks skipped (with task IDs)
   - List of commits created (hashes + messages)
   - Any test failures that existed before your changes (baseline failures)
   - The branch name of your worktree
```

## Step 4: Monitor and Merge

As agents complete their work packages:

1. **Check results**: For each completed agent, review:
   - Did all tasks get addressed (fixed or skip-documented)?
   - Did tests pass in their final run?
   - Are the commits logical and clean?

2. **Handle skipped tasks**: Collect all skipped tasks from `parity-reports/fix-parity-skipped-*.md` files. Present them to the user with reasons.

3. **Merge worktree branches**: After all agents complete:
   - Create a new integration branch from the current branch: `git checkout -b fix/parity-YYYY-MM-DD`
   - For each agent's worktree branch, merge it in: `git merge {worktree-branch} --no-ff -m "merge: {module} parity fixes"`
   - If merge conflicts occur, resolve them (the agent that touched the file most recently wins, but verify logic).
   - Run the full test suite on the merged branch.
   - If tests fail after merge, identify which merge caused the regression and fix it.

4. **Final verification**:
   - Run `cd pyjhora-web && npx vitest run` on the merged branch
   - Run `cd pyjhora-web && npx tsc --noEmit` to verify type checking passes
   - If both pass, the branch is ready.

## Important Guidelines

- **Nothing gets silently skipped**: Every single task from the parity report must be either FIXED or SKIP-DOCUMENTED with a clear reason. If an agent finishes without addressing all its tasks, flag it immediately and re-assign the missed tasks.
- **Tests are the gatekeeper**: No commit goes in with failing tests. Period. If a fix breaks tests, the fix is wrong — revert and try again.
- **Worktree isolation**: Each agent works in its own worktree to avoid conflicts. They should NOT touch files outside their assigned TS file (and its test file if it exists) unless absolutely necessary for the fix.
- **Read Python carefully**: The Python code is the source of truth. When in doubt, match Python exactly. Don't "improve" or "optimize" the TS version — match the Python logic precisely.
- **Persistent issues are red flags**: If an issue appeared in two consecutive parity reports, it was either missed or incorrectly fixed last time. Pay extra attention to these — verify the fix is truly correct.
- **Atomic work**: Each agent's branch should be independently mergeable. Don't create cross-agent dependencies unless absolutely necessary.
- **npm install first**: Every agent must run `npm install` in their worktree before doing anything. The worktree won't have `node_modules/`.
- **Baseline test run**: Every agent must run tests BEFORE making changes to establish which tests were already failing. Only new failures are regressions.
- **PRs only on AmitPhulera/PyJHora**: Never create PRs against any other repository.
